DAOT COMPAT — ПЕРЕДАЧА ЗАДАЧИ СЛЕДУЮЩЕЙ НЕЙРОСЕТИ
=====================================================

ПРОЕКТ: NeoForge 1.21.1 мод "daotcompat" — мост между Danny's AOT (Fabric-мод
через Sinytra Connector, только reflection, исходников нет) и Sable (физика
движущихся "sub-level" структур — кораблей Create: Aeronautics).

Репозиторий: https://github.com/MikasaAckerrman/daot-compat
Реальный код лежит НЕ в main, а в ветке feature/4-reflection-fix.
Собирается: JAVA_HOME=<jdk21> ./gradlew build -x test → build/libs/daotcompat-1.0.0.jar
Требуется JDK 21 (не 17, не 11).

СТЕК ПОЛЬЗОВАТЕЛЯ: NeoForge 1.21.1 + Sinytra Connector + Forgified Fabric API,
моды: Sable, Danny's AOT (через Connector), Create, Create: Aeronautics.

--------------------------------------------------
ЧТО УЖЕ СДЕЛАНО (в приложенном src/ и jar)
--------------------------------------------------

1. БАЗА (была готова до нас, ветка feature/4-reflection-fix):
   - HookTransformResolver / RemoteHookFollower — крюк ODM держится в локальных
     координатах Sable sub-level (корабля) и пересчитывается в мировые каждый
     тик через sl.logicalPose().transformPosition(...). Это чинит основной баг:
     "трос улетает в случайные координаты при зацепе за движущийся объект".
   - ThunderSpearFollower — то же самое для воткнувшихся громовых копий.
   - AOTReflect/RemoteHookReflect/SpearReflect/Reflect — безопасный доступ к
     закрытым классам AOT через reflection (no-op если AOT не установлен).
   - SableBridge/SubLevelResolver — безопасные обёртки над Sable API.

2. НАШИ ДОБАВЛЕНИЯ (round 1, СОБРАНО и проверено BUILD SUCCESSFUL):
   a) Фикс копий (ThunderSpearFollower.java):
      - Документирован порядок тиков (EntityTickEvent.Pre гарантированно
        раньше explode() AOT — взрыв не может использовать старые координаты).
      - Добавлен drift-лог при взрыве копья (сравнивает финальную позицию
        с последней известной — доказательство что фикс работает).
   b) Dimension guard (межмировая защита, Nether/End):
      - DynamicHookData (record) получил поле dimensionKey.
      - HookTransformResolver, RemoteHookFollower, ThunderSpearFollower теперь
        сверяют текущее измерение игрока/сущности с измерением, где был создан
        анкер крюка/копья — при несовпадении крюк сразу отпускается (drop())
        с debug-логом, вместо похода в Sable API с чужим UUID.
   c) Кнопка "подтянуться" (REEL_IN):
      - Новый keybind, по умолчанию LEFT_ALT (Options → Controls → DAOT Compat,
        ПЕРЕБИНДИВАЕТСЯ пользователем как любой ванильный keybind — да, это
        возможно и уже работает).
      - ReelControl.java — AOT сам применяет притяжение к крюку каждый тик
        автоматически (мы не можем менять это, только jar). Наш код работает
        ПОСЛЕ AOT (ClientTickEvent.Post, LOWEST priority): если кнопка REEL_IN
        не зажата — вычитает из скорости игрока компоненту "к крюку", оставляя
        гравитацию/боковую инерцию нетронутыми. Зажал кнопку — тянет как обычно.

ЧТО НЕ УСПЕЛИ / НАДО СДЕЛАТЬ ДАЛЬШЕ (round 2 — code review, НЕ применено к коду!)
--------------------------------------------------
Полный code-review уже проведён (см. секцию "НАЙДЕННЫЕ ПРОБЛЕМЫ" ниже), но
ФИКСЫ ЕЩЁ НЕ ВНЕСЕНЫ в приложенный src/ — это первая задача для следующей
сессии. Технический бриф с точными инструкциями fix'а для каждого пункта —
см. файл FIX_BRIEF.txt (передай его целиком кодинг-агенту/Code tool).

НАЙДЕННЫЕ ПРОБЛЕМЫ (приоритет High→Low):
1. [High] RemoteHookReflect.hooks() отдаёт live view WeakHashMap.values() —
   итерация по нему в RemoteHookFollower.tick() без внешнего lock рискует
   ConcurrentModificationException, если put/remove придёт с другого потока
   (например network packet handler). Фикс: возвращать defensive copy под
   synchronized(map) — см. FIX_BRIEF.txt пункт 6.
2. [Medium-High] WeakHashMap ключи — reflection-объекты хуков AOT. Если AOT
   переиспользует объекты хуков (object pooling), weak-ref никогда не станет
   unreachable — старые данные будут "залипать" на новом логическом крюке.
   Фикс: TTL-инвалидация (счётчик тиков, если анкер не подтверждался >100
   тиков — принудительно удалить) — см. FIX_BRIEF.txt пункт 2.
3. [Medium] MATCH_RADIUS_SQR = 65536 (256 блоков) при maxHookDistance≈250 у
   AOT — запас всего 6 блоков, слишком мало для быстро движущихся кораблей
   Sable (легитимный трос может ложно отцепиться). Увеличить запас до ~64
   блоков — см. FIX_BRIEF.txt пункт 3.
4. [Medium] Дублирующийся вызов HookTransformResolver.process ДВАЖДЫ за тик
   (из LocalPlayerTickMixin HEAD и из ClientTickEvent.Post) — лишняя нагрузка
   на reflection+transform. Оставить только один вызов — см. FIX_BRIEF.txt п.1.
5. [Low] ReelControl использует Vec3.ZERO как sentinel "нет хука" — путается
   с редким edge-case "хук физически в позиции игрока". Заменить на явные
   boolean-флаги — см. FIX_BRIEF.txt пункт 4.
6. [Оптимизация] SubLevelResolver.findContaining делает полный скан всех
   sub-level'ов каждый тик даже если игрок/сущность остались в том же корабле.
   Добавить sticky-кеш "последний известный sub-level" — см. FIX_BRIEF.txt п.5.
7. [Оптимизация] AOTReflect.getLeftHook/getRightHook дёргают Method.invoke()
   каждый тик — можно ускорить через MethodHandle вместо Method (после JIT
   прогрева быстрее в 2-10x). Не входит в FIX_BRIEF.txt, доп. идея на будущее.

--------------------------------------------------
БОЛЬШОЙ СЛЕДУЮЩИЙ ЭТАП: НАСТОЯЩАЯ ФИЗИКА ТРОСА (не начато)
--------------------------------------------------
Цель пользователя: ODM-снаряжение как в аниме — провисание троса, огибание
блоков, инерция, реалистичный свинг (как в модах "grappling hook").

Ключевая находка: Sable уже содержит ГОТОВЫЙ verlet-физический движок канатов:
  dev.ryanhcode.sable.api.physics.object.rope.RopePhysicsObject
  dev.ryanhcode.sable.api.physics.object.rope.RopeHandle (+ AttachmentPoint enum: START/END)
  dev.ryanhcode.sable.api.physics.PhysicsPipeline.addRope(RopePhysicsObject)

План интеграции (НЕ начато, следующая большая задача):
1. Вместо (или в дополнение к) текущей чисто визуальной отрисовки троса в
   daot.HookLineRenderer (процедурная синусоида, без физики, без коллизий) —
   создавать Sable RopePhysicsObject при зацепе крюка, регистрировать через
   PhysicsPipeline.addRope(), брать точки (List<Vector3d>) из RopeHandle для
   рендера вместо текущей линейной интерполяции.
2. Sable сам считает натяжение/провисание/коллизию с блоками — трос физически
   огнётся вокруг препятствий, как в grappling hook модах.
3. Импульс притяжения / инерция ODM — нужно спроектировать отдельно (это уже
   не Sable API, а собственная механика над физикой троса): вероятно через
   applyImpulse/applyLinearAndAngularImpulse из PhysicsPipeline на игрока
   (если игрок трактуется как physics body) либо через собственный velocity
   integrator похожий на текущий ReelControl, но с учётом натяжения троса
   Sable вместо жёсткой "точки-цели".
4. ВАЖНО: у нас нет доступа к исходникам AOT — вся текущая механика ODM
   (pull force, orbit, dual-hook) реализована ВНУТРИ AOT jar и недоступна для
   правки. Придётся либо (а) полностью заменять AOT-движение своим кодом,
   перехватывая и переопределяя его результат каждый тик (как сейчас делает
   ReelControl, но сложнее), либо (б) договориться об ограниченной интеграции
   (использовать Sable только для ВИЗУАЛА троса, оставив движение как есть).
   Это ключевое архитектурное решение, которое пользователь должен принять
   ПЕРЕД началом кодирования — обсуди с ним лично, не бросайся сразу писать код.
