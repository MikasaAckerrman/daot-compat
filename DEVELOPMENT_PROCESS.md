## ⚠️ ГЛАВНОЕ ПРАВИЛО

> **НЕ НАЧИНАЙ ПИСАТЬ КОД, ПОКА НЕ ПОНИМАЕШЬ ПРОБЛЕМУ**

Большинство AI ошибаются потому что:
- ❌ Видят первый баг и пытаются его чинить
- ❌ Чиня один баг, ломают три соседние системы
- ❌ Начинают "гадать" вместо анализа
- ❌ Не проверяют регрессии

Правильный подход:
- ✅ АНАЛИЗ → ПОНИМАНИЕ → ПЛАН → РЕАЛИЗАЦИЯ → ПРОВЕРКА

## 🔍 ЭТАП 3: НАЙТИ РАЗЛИЧИЯ (VANILLA vs PHYSICS)

### Самая критичная задача!

Проблема: одни и те же действия работают по-разному на обычных блоках и на физических объектах.

### Где искать?

```java
// В каждом файле ищи:
if (isPhysicsBlock) { ... }
if (isVanillaBlock) { ... }

// Или:
checkCollision(...) // может быть разная реализация
applyForce(...)     // может быть разная логика
getPosition(...)    // может кэшироваться по-разному
```

### Что определить

1. **На что влияет тип блока?**
   - Hook attachment?
   - Rope constraint?
   - Pull behavior?
   - Physics calculation?

2. **Где используется отдельная логика?**
   - Есть ли if/switch по типу блока?
   - Есть ли разные классы для разных типов?
   - Есть ли разные методы?

3. **Где происходит конфликт?**
   - Где две системы пытаются управлять одним?
   - Где одна система переписывает результат другой?

### ❌ ЗАПРЕТ
- Не начинать чинить!
- Только наблюдать и анализировать
- Только писать выводы в заметки


## 📝 ОБЯЗАТЕЛЬНЫЙ ПРОЦЕСС ПЕРЕД КАЖДЫМ ИЗМЕНЕНИЕМ

### Шаблон (ОБЯЗАТЕЛЕН)

Перед тем как писать код, ВСЕГДА заполнить:

```
ПРОБЛЕМА:
  Что именно не работает?
  (Конкретное наблюдение, не гадание)

ГИПОТЕЗА:
  Почему это происходит?
  (На основе анализа архитектуры)

ФАЙЛЫ К ИЗМЕНЕНИЮ:
  Какие файлы будут изменены?
  Почему именно эти?

ПОЧЕМУ БЕЗОПАСНО:
  Почему эти изменения не сломают остальное?
  Какие системы остаются нетронутыми?

ПРОВЕРКА:
  Как убедиться что исправление сработало?
  Какие регрессии искать?
```

### Пример ПРАВИЛЬНО

```
ПРОБЛЕМА:
  Left Hook воспроизводит звук много раз вместо одного.

ГИПОТЕЗА:
  playRopeHookSound() вызывается каждый тик в tick() методе.
  Нет debounce/cooldown механизма между вызовами.

ФАЙЛЫ К ИЗМЕНЕНИЮ:
  GrapplePhysicsController.java (добавить cooldown)

ПОЧЕМУ БЕЗОПАСНО:
  - Только добавим переменную leftHookSoundCooldown
  - Логика Pull/Rope/DEW остаются нетронутыми
  - Cooldown = 5 тиков, это не повлияет на игруглось
  - Другие звуки работают независимо

ПРОВЕРКА:
  - Зацепить левый крюк → 1 звук (не N)
  - Зацепить правый крюк → 1 звук (не N)
  - DEW звук остаётся независимым
  - Break звук работает как раньше
```

### Пример НЕПРАВИЛЬНО

```
ПРОБЛЕМА:
  В модуле много багов.

ГИПОТЕЗА:
  Может быть проблема с каким-то кодом.

ФАЙЛЫ К ИЗМЕНЕНИЮ:
  Много файлов.

ПОЧЕМУ БЕЗОПАСНО:
  Надеюсь что будет работать.

ПРОВЕРКА:
  Протестируем потом.
```

❌ ЭТОГО ДЕЛАТЬ НЕЛЬЗЯ! Это приводит к регрессиям.

## 🎮 РЕАЛЬНЫЕ ПРОБЛЕМЫ (ОРИЕНТИРЫ)

Эти проблемы были обнаружены при тестировании. Используй их как подсказки при анализе:

### 1. Left Hook нестабилен
- Повторные попытки зацепления
- Спам событий
- **Ориентир:** Ищи место где Left Hook обрабатывается отдельно

### 2. Разное поведение Vanilla vs Physics
- На обычных блоках: автоподтягивание
- На физических: только с SPACE
- **Ориентир:** Есть разделение логики, найди if/else

### 3. После отпускания SPACE
- Игрок опускается сам вниз
- Должен оставаться на длине
- **Ориентир:** Не очищаются силы/ограничения

### 4. W почти не даёт ускорения
- Функция существует
- Незаметна в игре
- **Ориентир:** Масштаб импульса неправильный

### 5. Rope проходит сквозь блоки
- Нет коллизии с физических объектов
- **Ориентир:** RopeSegmentHandler не учитывает Physics

### 6. DEW нестабилен
- Слишком большое ускорение
- Импульс накапливается
- **Ориентир:** Нет ограничения максимальной скорости

### 7. Reverse DEW незаметен
- Почти не работает
- **Ориентир:** Проверь весь код, может не реализовано

### 8. Звук повторяется
- Странный звуковой эффект
- **Ориентир:** Уже исправлено в v1.3.4 (cooldown)

### 9. После отпускания троса
- Медленное падение как будто трос есть
- **Ориентир:** Ограничение не сбрасывается

### 10. Общий конфликт систем
- Системы борются между собой
- **Ориентир:** Ищи места где две системы пишут в один параметр

## 🚨 АНТИПАТТЕРНЫ (ЗАПРЕЩЕНО)

### ❌ ЗАПРЕЩЕНО ЭТО

1. **"Быстрое" исправление**
   ```
   Я вижу проблему → сразу пишу код
   ❌ Это приводит к регрессиям
   ```

2. **Исправление симптомов**
   ```
   Звук спамит → добавлю флаг
   ❌ Нужно исправить причину (вызов каждый тик)
   ```

3. **Множественные изменения**
   ```
   Разом менять Hook, Rope и Physics
   ❌ Невозможно отследить что сломалось
   ```

4. **Гадание вместо анализа**
   ```
   "Может быть здесь проблема?" → меняю код
   ❌ Основывать изменения на фактах, не предположениях
   ```

5. **Пропуск регрессионной проверки**
   ```
   Исправил одно → не проверил остальное
   ❌ Каждое изменение может сломать соседние системы
   ```

## ✅ ПРАВИЛА КОТОРЫХ ПРИДЕРЖИВАТЬСЯ

1. **Анализ прежде всего**
   - Понять проблему
   - Понять причину
   - Только потом - решение

2. **Одна система за раз**
   - Изменить одно
   - Проверить всё остальное
   - Только потом - следующее

3. **Документировать шаги**
   - Перед кодом: описать что и почему
   - После кода: описать что изменилось

4. **Проверять регрессии**
   - Всегда после изменения
   - Не "потом"
   - Не "надеюсь"

5. **Сохранять рабочее**
   - v1.3.4 работает
   - Не переписывать без необходимости
   - Только точечные исправления
