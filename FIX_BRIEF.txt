## Фикс 1 — Убрать дублирующийся вызов HookTransformResolver.process за тик
Сейчас `HookTransformResolver.process(level, hook)` для локального игрока вызывается ДВАЖДЫ за один client tick: один раз из `mixin/client/LocalPlayerTickMixin` (HEAD инъекция в `LocalPlayer.tick()`), второй раз из `DAOTCompat`'s `ClientTickEvent.Post` LOWEST listener. Прочитай оба места и их комментарии. `HookTransformResolver.process` идемпотентен на тех же входных данных в рамках одного тика (просто перезаписывает AOT-хук позицию через `AOTReflect.setPosition`, повторный вызов с той же исходной AOT-позицией не меняет результат вредно, но это два лишних reflection-invoke + Sable transform в тик просто впустую).
Оставь ТОЛЬКО вызов из `ClientTickEvent.Post` (он видит финальное состояние — AOT уже отработал свой ClientTickEvent к этому моменту, значит это правильная точка перехвата), и удали вызовы `HookTransformResolver.process(...)` и `RemoteHookFollower.tick(...)` из `LocalPlayerTickMixin` — оставь миксин файл только если он больше не нужен вообще, удали его целиком (и удали mixin entry из `daotcompat.mixins.json`) если после этого он становится пустым/бесполезным. Если удаление миксина полностью убирает какую-то нужную гарантию порядка — задокументируй в JavaDoc комментарии в `DAOTCompat.java` почему `ClientTickEvent.Post` LOWEST достаточен (AOT сам регистрируется через Fabric `ClientTickEvents.END_CLIENT_TICK`, которое NeoForge/Connector должно вызывать в рамках обычного client tick до нашего `ClientTickEvent.Post` LOWEST — если не уверен на 100% в порядке относительно Fabric API моста, оставь миксин но добавь простой guard: статическое `boolean` поле `processedThisTick`, устанавливаемое в true после первого вызова за тик и сбрасываемое в начале следующего тика (используй `ClientTickEvent.Pre` LOWEST-priority listener в `DAOTCompat` чтобы сбрасывать флаг), чтобы гарантировать ровно один реальный проход даже если оба хука остаются подписаны). Выбери сам наиболее безопасный вариант и явно объясни выбор в комментарии.

## Фикс 2 — TTL-инвалидация вместо чистой опоры на WeakHashMap GC
В `RemoteHookFollower.java` (класс `Anchor`) и в `ThunderSpearFollower.java` (map `ANCHORS`) добавь механизм TTL: если запись не была "подтверждена" (её follow()/onTick() обработка происходила) дольше N тиков — считать её протухшей и принудительно удалить, а не полагаться только на weak-reference GC (обоснование: если AOT переиспользует объекты хуков через пул, weak-key никогда не станет unreachable, и старые transform-данные будут молча применяться к новому логическому крюку). Реализация: добавь `long lastSeenTick` (используй простой статический счётчик тиков внутри каждого класса, инкрементируемый в начале каждого их tick()/onTick() вызова, НЕ полагайся на `System.currentTimeMillis()` для этого — используй монотонный tick counter) в `Anchor` (RemoteHookFollower) и в отдельную wrapper-структуру для `ThunderSpearFollower.ANCHORS` (можно завести небольшой internal record `TrackedAnchor(DynamicHookData data, long lastSeenTick)` вместо хранения чистого `DynamicHookData"` как value в map). Порог: 100 тиков (5 секунд) без обновления — считать протухшим и удалить с debug-логом "stale anchor removed (possible AOT object pooling)".

## Фикс 3 — Увеличить запас MATCH_RADIUS_SQR в HookTransformResolver
Текущее `MATCH_RADIUS_SQR = 65_536.0` (256²) при вероятном `maxHookDistance` AOT около 250 блоков даёт всего ~6 блоков запаса — недостаточно для быстро движущихся Sable-кораблей (относительная скорость игрок+корабль может съесть этот запас за 1 тик и ложно отцепить легитимный трос). Увеличь запас: `MATCH_RADIUS_SQR = Math.pow(250.0 + 64.0, 2)` (то есть ~314 блоков радиус, запас 64 блока) — добавь именованную константу `HOOK_RANGE_MARGIN = 64.0` с комментарием объясняющим reasoning (быстро движущийся sub-level может преодолеть много блоков за один client tick при высокой скорости, нужен запас чтобы не ложно отцеплять валидный трос). Не переусердствуй — не убирай защиту полностью, просто расширь порог с обоснованным числом.

## Фикс 4 — Явный boolean sentinel вместо Vec3.ZERO в ReelControl
В `ReelControl.apply()`: замени неявную семантику "toHook length <= 1e-3 значит нет хука" на явные boolean флаги, чтобы не путать "хука нет" с "хук физически в позиции игрока" (редкий но возможный edge-case при телепортах/сетевых лагах). Рефактори с явными `boolean leftContributed` / `boolean rightContributed` флагами, не меняя остальную логику усреднения направлений.

## Фикс 5 — Micro-optimization: избегать полного queryIntersecting скана в SubLevelResolver, если сущность/игрок остаётся в том же sub-level между тиками
В `SubLevelResolver.findContaining` (используется из `HookTransformResolver.attach()`, `RemoteHookFollower.follow()`, `ThunderSpearFollower.onTick()`) добавь простой "sticky" fast-path кеш: перед полным `container.queryIntersecting(box)` сканом всех sub-levels, сначала проверь один явно переданный "подсказка" sub-level (если он есть и валиден) через тот же `intersects` тест, и возвращай его сразу если совпадает — избегая полного скана в частом случае "то же самое место что и в прошлый раз". Сделай это через новый overload `findContaining(Level level, Vec3 pos, @Nullable SubLevel hint)` (сохрани старый однопараметровый метод как `findContaining(level, pos, null)` для обратной совместимости с существующими вызовами, которые пока не передают hint — это не обязательно менять все три caller'а сразу, но если легко — прокинь `anchor`-based hint в местах где он уже под рукой, например `HookTransformResolver.follow()` уже знает текущий `sl` перед вызовом `SubLevelResolver.findContaining` в другом контексте — не путай методы attach() vs follow(), attach() не имеет предыдущего sl, но если по логике где-то есть — используй).

## Фикс 6 — Убедиться WeakHashMap synchronizedMap безопасен при итерации
Проверь ВСЕ места где происходит `for (X x : someWeakHashMapBackedCollection)` (например `RemoteHookFollower.tick()` через `RemoteHookReflect.hooks()` который возвращает `map.values()` напрямую — это НЕ снимок, а live view, итерация по live view synchronizedMap без внешнего lock блока — риск ConcurrentModificationException, если put/remove происходит из другого потока во время итерации, например network packet handler). Исправь `RemoteHookReflect.hooks()` чтобы возвращать defensive copy (`new ArrayList<>(map.values())`) СНЯТУЮ под тем же монитором что и остальные операции (используй `synchronized(MAP) { return new ArrayList<>(MAP.values()); }` где `MAP` — тот же объект, на котором `Collections.synchronizedMap` был вызван — то есть сохрани ссылку на map ДО того как обернуть в synchronizedMap, чтобы можно было synchronized на неё явно, либо просто synchronized на сам synchronizedMap объект, что тоже работает так как Collections.synchronizedMap использует this как mutex по умолчанию). Обноври вызывающий код в `RemoteHookFollower.tick()` соответственно (тип возвращаемого значения меняется с `Collection<?>` на `List<?>` или похоже — обнови сигнатуру).
